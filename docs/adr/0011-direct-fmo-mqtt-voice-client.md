# 0011：采用 App 独立身份的 FMO MQTT 语音客户端

**日期：** 2026-08-23

**状态：** Accepted

**取代范围：** ADR-0001 与 ADR-0009 中对 FMO MQTT 语音收发、Opus 编解码和 App PTT 的排除；盒子私钥提取、盒子身份复用和本地 `/audio` 边界不变

## 背景

项目建立时，FMO MQTT 语音线格式、软件客户端 vendor 和完整 SAS 鉴权输入尚未形成足够公开的实现依据，因此 ADR-0001 排除了完整语音客户端，ADR-0009 只批准盒子局域网 `/audio` 的固定 PCM 接收。

此后官方公开了 FMO 语音数据协议，明确允许 PC/Web/SDK 等无硬件实现使用 `0x2000...0x2FFF` 软件 vendor 区；SAS 源码与文档公开了证书包、12 元确定性 CBOR proof、Ed25519 验证、时间窗和 `FMO/RAW` ACL；证书工具也公开了 App 可复用的 User Certificate 格式。用户自建服务器上的独立 App 身份已完成发送和接收脚本闭环。

## 考虑的方案

1. **继续只做盒子伴侣：** 风险最低，但无法满足用户在没有盒子参与时直接收听和 PTT。
2. **复用盒子证书/私钥：** 表面兼容性高，但破坏设备身份边界、密钥不可迁移原则和服务器审计，明确拒绝。
3. **App 独立密钥、证书与软件 vendor：** 自建网络由管理员信任 App Root，未来官方签发通过 Provider 接入；语音层遵守公开线格式。

## 决策

采用方案 3：

- App 本地生成并持有独立 Ed25519 私钥，通过 `ClientIdentityProvider` 提供签名能力；语音与 MQTT 层永远拿不到裸私钥。
- 自建网络使用管理员显式信任的 Root/Intermediate 为 App 公钥签发 User Certificate；未信任该 Root 的服务器应正常拒绝。
- 未来官方若开放 App 证书审批/签发，新增 `OfficialIdentityProvider`，不修改 SAS、MQTT、FMO/RAW、Opus 或 PTT 核心。
- App 不读取、导出、导入或复用盒子私钥，不冒用盒子 UID、官方 `vendor = 0x0000` 或任何已登记硬件 vendor。
- MQTT 只通过 SAS 公开的证书 proof 鉴权；每次 CONNECT 生成新的 timestamp 与签名，服从证书链、CRL、服务器角色和 ACL。
- 首版只承诺前台 MQTT 收听与按住 PTT；后台系统 PTT 需要 PushToTalk framework、APNs 服务和新评审。
- 实时语音只在有界内存中处理，不录音、不持久化、不进入日志或分析。
- 具体字段、状态机、安全和验收门槛以 [计划 0010](../plans/0010-direct-fmo-voice-client.md) 为准。

## 后果

### 正面

- App 可以作为公开协议定义的软件终端工作，不再依赖盒子转发音频。
- 自建身份和未来官方身份共享同一业务协议，避免把一次性自建 CA 方案写死进语音核心。
- 独立 App 身份使服务器管理员能够单独信任、吊销、限权和审计，不污染盒子身份。

### 负面

- 新增 MQTT、libopus、麦克风、实时音频、路由仲裁和证书生命周期复杂度。
- 自建 Root 不具备官方网络的自动准入；其他服务器是否接受由各管理员决定。
- 明文 MQTT 1883 暴露元数据和语音，生产部署需要 TLS 或明确风险提示。
- iOS 普通 socket 不能保证后台常驻；系统级后台体验需要额外服务端和 entitlement。

### 中性

- 现有盒子局域网 `/audio` 仍是独立的只接收来源，不因本决策改为可发送或通用代理。
- vendor 只标识实现来源，不参与 SAS 鉴权，也不解决 UID 唯一性。
- 用户资格、服务器规则和可能发生的远端射频发射仍由持证用户与服务器管理员负责。
