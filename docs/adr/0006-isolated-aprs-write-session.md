# 0006：隔离 APRS 只读与写会话

**日期：** 2026-08-07

**状态：** Accepted

## 背景

0.4 的 FMO 网络以 `pass -1` 和 `u/APFMO4` 提供只读接收，并在独立信任链中验证 FMO V4。0.6 需要使用按呼号计算的 PASSCODE 建立验证登录，发送标准 APRS 消息、ACK 和三种 FMO 远控命令。

若直接把发送方法加入 0.4 接收器，地图、目录、事件或未来解析代码会在类型层面取得发送能力；登录状态、过滤器、重连和故障也会互相影响。反之，完全复制网络栈会造成 CRLF、TNC2 和取消行为漂移。

## 考虑的方案

1. **把 0.4 会话升级成单一读写连接：** 连接数最少，但放大写权限范围，并把 FMO V4 信任与消息交付状态耦合。
2. **隔离业务会话，共享底层安全原语：** 只读与写会话分别拥有 transport 实例和登录状态机，共享 endpoint、CRLF framer 与 TNC2 地址/解析类型。
3. **完全独立实现第二套网络栈：** 隔离最彻底，但边界校验和取消语义容易漂移。

## 决策

采用方案 2：

- `APRSISReceiving` 永久保持 0.4 的 `pass -1` 只读契约，不新增业务发送方法。
- `APRSISMessaging` 使用单独的 Network.framework transport 和 `verified` 登录，只在 App 活跃且身份存在时运行。
- 两条会话共享有界 CRLF、TNC2 地址/解析和 APRS-IS endpoint 类型，但实例、登录响应、过滤器、任务、退避和断开互不复用。
- 写会话不公开任意字节发送；上层只能提交经标准消息编解码器或固定远控编解码器生成的单行帧。
- PASSCODE 按需计算且不持久化。SECRET 仍属于远控模块，只进入 Keychain。

## 后果

### 正面

- 0.4 地图/事件代码在类型层面继续无法发送数据，既有只读信任边界不回退。
- 消息重试、ACK 与远控单次发送不会改变 FMO V4 接收和验证生命周期。
- 共享 framer/TNC2 基础类型，避免重复实现关键输入边界。

### 负面

- App 前台可能同时保持一个只读连接和一个验证写连接，增加少量连接与能耗。
- 两条会话需要分别处理登录、断线和重连状态，测试矩阵更大。

### 中性

- 本决策不授权后台常驻、任意 APRS 帧、局域网写命令或绕过 PASSCODE/SECRET。
- 若未来 APRS-IS 服务明确限制同身份多会话，可用新 ADR 评估合并 transport，但不得让只读业务层获得写接口。
